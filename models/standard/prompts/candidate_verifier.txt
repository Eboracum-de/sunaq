RULES
1. A candidate must be substantively relevant to the request. The words of the user question do NOT need to occur literally, in the same inflection, or in the same language.
2. Use QueryFrame as the target structure: entities, roles/direction, relations, constraints, and concepts. Do not impose a fixed document ontology. If the user requests a document type, however, that document type is a real eligibility condition: the candidate document itself must be of that type. A mere mention, accounting entry, attachment reference, or reference to such a document is insufficient and is reject.
3. Produce one EvidenceFrame per document:
   - entities: only entities supported by the document itself; role remains free-form.
   - relations: only relations supported by this document itself; predicate remains free-form.
   - constraints: criteria observed in the document with status=match/conflict/unclear relative to the request.
   - concepts: important subject concepts directly addressed by the document.
   - mentioned_entities: entities that are merely mentioned, quoted, or referenced through another document or transaction.
4. Years, exact dates, identifiers, or complete filenames supplied under SAFE EXPLICIT CONSTRAINTS are binding for status=match. If the relevant evidence is absent, use uncertain. If the document clearly assigns the requested event to a conflicting value, use reject.
5. Bind entities to the user's actual information need.
   - For a concrete role, relationship, or document-type request, THE DOCUMENT ITSELF must support that exact role direction, relationship, or requested document type. A mere mention, quotation, reference to another document number, or related transaction is insufficient.
   - A request consisting essentially of one entity name (for example "Example Holdings GmbH") is a broad entity/information request. A document is directly relevant when it contains substantive facts clearly attributable to that entity. The entity need not be the document's main subject or the original chat's main subject.
   - For source_origin=chat_archive, technically substantive source/document/Elasticsearch excerpts reproduced inside the archived chat are part of the verifiable chat content. If such an excerpt assigns concrete properties, people, roles, holdings, addresses, or transactions to the requested entity, that is NOT merely a reference. Being inside an excerpt, quotation, or cross-reference does not make it reference_only.
   - relation_binding=direct: the document itself contains substantive information clearly attributable to the requested entity for the information need. For broad entity requests, this also includes substantively useful cross-references and source/search excerpts.
   - relation_binding=reference_only: the requested entity/relationship/document number is merely named or cited without a usable fact attributable to it; status=reject.
   - relation_binding=contradicted: the document itself supports a different or opposite role/relationship assignment; status=reject.
   - relation_binding=unclear: OCR/layout loss or insufficient content prevents reliable binding; status=uncertain.
6. Company names may occur as full names or clearly recognizable short forms present in the document. Do not invent aliases.
7. Graph aliases or other external identity assumptions are valid only when explicitly supported by supplied context.
8. Do not require artificial field labels or exact visual layout. Linearized PDF/OCR/Office text is not uncertain merely because visual placement was lost.
9. Use status=match only with sufficient document evidence; uncertain for plausible but not reliably established binding; reject for clear non-matches.
10. Return exactly one entry for every supplied document.
11. When evidence remains ambiguous, prefer uncertain over invented certainty.
